# Как вносить изменения

Бот работает в живой беседе: каждая ошибка видна людям, а не только в логе.
Отсюда два правила, которые важнее стиля кода.

---

## Новая возможность приходит выключенной

Всё, что меняет поведение бота на виду у людей, должно закрываться
переменной окружения `YARANIMKA_*` **со значением по умолчанию «выключено»**.

Так уже сделано со всем заметным:

| Переменная | Что закрывает |
|---|---|
| `YARANIMKA_COMMANDS` | ответы на команды в беседе |
| `YARANIMKA_WATCH` | поиск раздач и правку сообщения |
| `YARANIMKA_SEASON` | сезонные напоминания |
| `YARANIMKA_LEAVE_NOTIFY`, `YARANIMKA_LEAVE_KICK` | охрану беседы |
| `YARANIMKA_NEWS` | блок новостей (ноль убирает) |
| `YARANIMKA_ADULT`, `YARANIMKA_ADULT_SEARCH` | взрослое в дайджесте и в поиске |

Смысл в том, что вмёрженный код и включённая возможность — разные события.
Правку можно принять, выкатить на сервер и посмотреть, ничего не сломав;
включить — отдельным движением, когда будет уверенность. И выключить обратно
правкой одной строки в `.env`, без пересборки образа и без отката коммитов.

Как это выглядит в коде:

```python
# config.py — по умолчанию выключено
horoscope: bool = field(default_factory=lambda: _bool("YARANIMKA_HOROSCOPE"))

# bot.py — ранний выход, а не разбросанные проверки
def horoscope(self) -> str:
    if not self._cfg.horoscope:
        return ""
    ...
```

Плюс строка в `.env.example` с объяснением, зачем оно нужно, и строка
в таблице переменных в `README.md`.

**Что под правило не подпадает:** исправления ошибок, правки текстов,
документация, тесты, ускорения. Флаг нужен новому поведению, а не починке
старого.

---

## Изменение должно откатываться

Любой мёрж возвращается назад одной командой:

```
git revert -m 1 <хеш мёрж-коммита>
```

`-m 1` означает «оставить ту ветку, в которую мержили» — то есть `main`.
Без этого ключа git не знает, какую из двух родительских веток считать
основной, и откажется.

Откат в репозитории и откат на сервере — разные вещи. На сервере нужно ещё
подтянуть изменения и перезапустить процесс, иначе там продолжит крутиться
старая сборка. **Быстрее всего выключить возможность в `.env`** и вернуться
к коду потом, на свежую голову.

Историю переписывать не нужно: `git revert` создаёт новый коммит, а не
стирает прошлое, и на чужих копиях репозитория это ничего не ломает.

---

## Перед тем как отправлять

```
python -m pytest tests -q
```

Тесты сетью не пользуются и идут пару секунд. Они же прогонятся
автоматически на каждый pull request.

К правке поведения нужен тест. Полезнее всего тот, который **падал бы
до неё** — иначе непонятно, что именно он стережёт. Пример из истории
проекта: заголовок дайджеста дважды печатал дату, а тест это пропускал,
потому что проверял вхождение подстроки, а не её количество.

Комментарии в коде объясняют **почему**, а не что. «Ходим на shikimori.io,
потому что shikimori.one непредсказуемо отвечает 403» — полезно. «Отправляем
запрос» — нет.
